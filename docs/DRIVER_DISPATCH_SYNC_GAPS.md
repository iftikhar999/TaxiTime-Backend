## Driver ↔ Dispatch Real-Time Sync Audit

This note captures where the driver app (v1) and the dispatch portal are out of sync today, what the behavior should be (based on the TaxiTime v0 implementation and current requirements), and what actually happens in the latest codebase.

### Desired, Actual, and Gap (per capability)

| Capability | Expected Flow | Current Behavior | Gap / Impact |
| --- | --- | --- | --- |
| **Shift lifecycle & logout** | Flow: `ShiftContext` registers start → `POST /api/mobile/driver/shift/start` persists row (`Shift.status=ONLINE`) → driver socket joins `/driver` namespace → on logout or session expiry, driver app calls `POST /api/mobile/driver/shift/end`, emits `goOffline`, backend updates shift (`status=OFFLINE`, `endTime`), removes driver from queues, and broadcasts `driverOffline` + `driver:status:update`. Dispatch drops the driver row, map marker, and queue counts instantly. | `driverShift.js:/end` now triggers queue cleanup + `driverOffline` (added in v1 patches). But the mobile logout button only clears AsyncStorage and disconnects from GraphQL; it **does not** hit `/shift/end` or emit `goOffline`. `server.js` disconnect handler is a no-op, so the shift row stays `ONLINE`, meaning `/dispatch` still receives the driver from the `GET_ONLINE_DRIVER_LIST` endpoint and keeps them rendered. | Real-world effect: dispatchers see drivers who have already logged out. Remedy requires (a) driver app logout to call `/shift/end` and `socket.emit('goOffline')` before clearing auth; (b) backend `driverNamespace.on('disconnect')` to call `queueManagementService.handleDriverStatusChange(driverId, 'OFFLINE')` plus `driverOffline`. |
| **Driver status states** | Contract: `AVAILABLE` (online/free), `BUSY` (any active ride phase: accepted/Roger/on_the_way/arrived/started), `AWAY` (manual break), `OFFLINE` (shift ended). Backend maintains canonical state in `Shift.status` and in queue metadata, and emits `driver:status:update` with `{driverId, status, zone, jobId}` whenever the state transitions. Dispatch store merges this into `drivers[]` immediately. | Mobile v1 keeps a local `driverStatus` in `ShiftContext`, but most transitions are applied via REST (`PUT /driver/shift/status`) and happen on screen taps only. Automatic transitions (job accepted, meter start, completions) don’t emit socket events. Dispatch `useDispatchController` subscribes to `driver:status:update`, yet because the driver app doesn’t broadcast, the store still reflects the previous status until the periodic REST fetch runs. | Implement a single source of truth: (a) driver app must emit `driver:status:update` via socket for every lifecycle change (assignment -> BUSY, manual away -> AWAY, job completion -> AVAILABLE); (b) backend should translate ride events (`job_assigned`, `meter:started`, `job:completed`) into status updates if the driver hasn’t sent one; (c) dispatch should trust socket updates and stop polling status. |
| **Location streaming** | Background location service posts `locationUpdate` to driver socket every few seconds while shift is active. Backend `trackingService` updates location table, re-evaluates zone membership, and emits `driverLocationUpdate` to `/dispatch` with lat/lng/speed/heading. When driver goes offline, a final `driverOffline` clears them from map and queue. | Streaming works while the app is foregrounded, but when the app is backgrounded and the OS kills it (or user logs out), no final update is sent; the server never receives `goOffline`, so markers remain on the map (dispatch uses last known coordinates). Additionally, dispatch doesn’t prune markers when `driverOffline` is missing. | Solutions: (a) driver app background service must send a “last gasp” update + `goOffline` before stopping; (b) backend disconnect handler must call `trackingService` to mark driver as offline and optionally broadcast a null location; (c) dispatch map should remove markers whenever `driverOffline` arrives or when a driver hasn’t updated within a TTL (fallback). |
| **Zone and queue membership** | `QueueManagementService` listens for status/location changes. When driver is `AVAILABLE`, they are inserted into the zone queue (`zone.queue`, `dispatch:zone_queue_updated`). When status becomes `BUSY`, `AWAY`, or `OFFLINE`, driver is removed. Dispatch zone panel listens to `zone_queue_updated` to keep counts accurate. | `handleDriverStatusChange` is invoked during explicit status updates and when `/shift/start`/`/shift/end` run. But if the app logs out without hitting `/shift/end`, there is no call. Even during a job, if driver becomes `BUSY`, the app doesn’t call `/shift/status`, leaving them in the queue (dispatch shows them as available in that zone). | Fix requires: (a) driver app to call `/shift/status` or emit a socket event with status whenever job state changes; (b) backend ride handlers to call `queueManagementService.handleDriverStatusChange` based on ride status (accepted → BUSY, completed → AVAILABLE); (c) add a periodic cleanup script to remove drivers whose last update is stale, as a guardrail. |
| **Job lifecycle telemetry** | Requirements from v0: dispatch sees live metrics once the job becomes active—`elapsedTime`, `waitingTime`, `distanceTravelled`, `currentSpeed`, `motionState`, `fareBreakdown` (base, distance, time, waiting, surcharges). These come from driver meter events: `meter:started`, repeated `meter:update` (every 5s or when values change), and `meter:stopped`. Dispatch UI updates the focused job panel in real time. | Backend does forward the raw `meter:*` events, but the driver app v1 doesn’t emit them. Instead, it relies on backend-generated ride updates after completion. Dispatch’s `handleJobUpdated` path treats `meter:*` as general job updates, so even if we started emitting, we’d need to extend the store to hold meter telemetry. | Action items: (a) resurrect the meter integration found in TaxiTimeVersiontwo’s `socketService`; (b) ensure driver app captures distance/time/waiting stats (from native tracker or Google Directions); (c) update backend event schema to include typed telemetry; (d) augment dispatch store/UI (e.g., `JobDetailsModal`) to display `liveFare`, `elapsed`, `waiting`, `speed`, `motion`. |
| **Job completion → driver availability** | After `job:completed`, the system should immediately mark driver `AVAILABLE` (unless driver explicitly ends shift). Queue manager re-adds them to the zone queue; dispatch receives `driver:status:update` and `zone_queue_updated`. | Currently `job:completed` in `server.js` updates the `Job` record and emits event, but there is no automatic shift update. It depends on driver hitting “Complete” in the app, which may or may not call `/shift/status`. If the app crashes after completion, dispatch keeps the driver stuck in BUSY. | Add a backend hook: after `job:completed`, call `queueManagementService.handleDriverStatusChange(driverId, 'AVAILABLE')` (guarded if shift already offline). Driver app should still send the status change to keep state in sync, but the backend must not rely on it. |
| **Socket lifecycle resilience** | Expected: driver app maintains a resilient socket connection (auto-reconnect with exponential backoff). When the socket drops, backend should treat it as driver offline after grace period (mark shift offline, remove from queue, broadcast). The app, on reconnect, should resync current status/location/job. | V1 still leans on REST; socket usage is partial. `socketService.js` from v0 had full reconnect logic, but v1’s `useDispatchSocket` / driver sockets don’t. Backend `driverNamespace.on('disconnect')` just logs “Driver disconnected” without cleanup. | Implementation plan: (a) port v0 `useDriverWebSocket` reconnect logic into v1; (b) on backend, add disconnect cleanup and maybe a heartbeat timeout; (c) ensure driver app replays pending status/location on reconnect so dispatch state doesn’t regress. |

### Key Remediation Steps

1. **Driver App**
   - **Logout/offline flow:** before clearing auth, call `POST /api/mobile/driver/shift/end`, await success, emit `socket.emit('goOffline', driverId)`, and only then stop background services.
   - **Status propagation:** centralize status transitions (assignment, Roger, arrival, completion, manual away) in a single manager (`enhancedDriverStatusManager.ts`) that fires both REST (`/shift/status`) and socket `driver:status:update`.
   - **Meter telemetry:** re-enable the meter worker to emit `meter:started`, periodic `meter:update` (with elapsed, waiting, distance, speed, fare components), and `meter:stopped`.
   - **Reconnect logic:** reuse v0’s `useDriverWebSocket` reconnection/backoff; on reconnect, re-send current status, zone, job ID, and last location snapshot.

2. **Backend**
   - **Socket disconnect cleanup:** in `server.js` `driverNamespace.on('disconnect')`, call `queueManagementService.handleDriverStatusChange(socket.userId, 'OFFLINE')`, emit `driverOffline`, and mark `Shift` offline if no active connection remains.
   - **Ride status hooks:** update handlers for `job_assigned`, `meter:started`, `job:completed`, and cancellations to call `handleDriverStatusChange` with appropriate state transitions.
   - **Telemetry typing:** define a shared TypeScript type (shared utils) for `meter:update` payloads, validate inbound data, and forward enriched telemetry to dispatch.
   - **Stale data sweep:** add a cron/worker to mark shifts offline if `locationUpdates` or socket heartbeats are stale, preventing ghost drivers.

3. **Dispatch Portal**
   - **Socket-first store updates:** prioritise `driver:status:update`, `driverOffline`, `zone_queue_updated`, `meter:*` events in `useDispatchController`; reduce reliance on REST polling.
   - **Live job display:** extend `DispatchJob` interface and job components to show live fare, elapsed time, waiting time, speed, and motion state.
   - **Driver roster cleanup:** when `driverOffline` arrives (or when no location updates for a set duration), remove driver from `drivers[]` and map markers.
   - **Diagnostics:** add a small admin panel showing per-driver last event timestamps to quickly detect stuck or stale sessions.

With these adjustments we regain the real-time parity that TaxiTime v0 had, matching the required four-status lifecycle, accurate zone queues, and live job telemetry.
